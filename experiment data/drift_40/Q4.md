# SalesX Product Documentation — Q4 Assurance Release

> **Authoritative snapshot:** version `q4.40`, effective for support cases occurring in Q4. This is a complete snapshot, not a diff.

## Documentation contract

SalesX is a multi-tenant CRM and revenue-operations platform for accounts, contacts, leads, opportunities, activities, products, workflows, integrations, analytics, and customer collaboration. This documentation defines support behavior for the Enterprise plan unless a signed order form is explicitly identified. Customer-specific contracts may alter commercial entitlement but never silently bypass product security controls.

A support answer must identify the governing behavior, accountable role, supported procedure, and material exception. Article keys are stable across releases and are the citation unit for the benchmark. Earlier snapshots remain valid only for events that occurred while they were effective.

## Service boundaries and shared vocabulary

- A **workspace** is the security, configuration, data, and billing boundary used by one customer environment.
- **Production** contains live business data. A **sandbox** is isolated and cannot be treated as a backup.
- The **Workspace Owner** holds ultimate customer authority. Administrators operate product configuration; specialized owners govern billing, security, data, integrations, reports, and onboarding workstreams.
- **Effective access** means the result after every grant, sharing path, field constraint, and denial is evaluated.
- A **support exception** exists only when this documentation or a verified written approval defines it. Support agents must not invent exceptions.
- All unspecified timestamps are UTC. Audit evidence must exclude passwords, access tokens, client secrets, payment credentials, and unredacted protected payloads.

## Q4 release notes

The Assurance release supersedes Q3. Forty article-level decisions changed. These changes affect workflows or policy semantics and form the release's controlled real-concept-drift set.

### Billing changes

- **[Invoice lifecycle and corrections](#billing-invoices)** (`billing.invoices`)
  - Previous behavior: An issued invoice is immutable; corrections use a credit memo and, when necessary, a replacement invoice linked to the original.
  - New behavior: Issued invoices remain immutable, but Billing Managers can now submit a structured self-service correction that atomically creates a linked credit memo and replacement invoice after validation.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Renewal process](#billing-renewals)** (`billing.renewals`)
  - Previous behavior: Unless the order form states otherwise, the subscription renews for the stated renewal term using the committed products and quantities on the renewal quote.
  - New behavior: Renewal is now confirmation-based for materially changed product bundles: unchanged renewals follow the order form, but a bundle migration requires an authorized Billing Manager to accept the mapped renewal proposal.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Access and data after subscription expiry](#billing-expiry_data)** (`billing.expiry_data`)
  - Previous behavior: At service end the workspace becomes inaccessible to ordinary users, enters a documented retention period, and is later securely deleted unless a legal hold applies.
  - New behavior: At service end the workspace enters a staged closure: ordinary access stops, authorized export remains available for a documented retrieval window, legal holds freeze eligible records, and deletion begins only after both the retention and hold checks clear.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Invoice disputes](#billing-disputes)** (`billing.disputes`)
  - Previous behavior: A dispute must identify the invoice, line item, reason, and evidence; undisputed amounts remain payable while SalesX investigates.
  - New behavior: Invoice disputes now separate disputed and undisputed ledger portions; the customer submits line-level reason and evidence, undisputed amounts continue through collection, and resolution creates a linked decision record and any required accounting document.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Plans and feature entitlements](#billing-plans)** (`billing.plans`)
  - Previous behavior: Feature access now resolves from a versioned entitlement manifest combining the workspace plan and active add-ons; Administrators may assign only permissions exposed by that manifest, and commercial entitlement still does not itself grant user access.
  - New behavior: Feature access now resolves from an effective-dated entitlement manifest, and a plan or add-on change first produces an impact preview of features that will activate, become read-only, or require migration; user permissions remain a separate decision.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Trial conversion](#billing-trial_conversion)** (`billing.trial_conversion`)
  - Previous behavior: Trial conversion now creates a pre-conversion inventory: customer records and approved configuration are retained, sample data is removed unless explicitly preserved, and paid usage begins only after the inventory and order activation both succeed.
  - New behavior: Trial conversion now uses a signed conversion manifest that classifies retained configuration, customer records, sample data, and unsupported trial features; activation is atomic and rolls back to the trial if the paid entitlement check fails.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Proration and co-termination](#billing-proration)** (`billing.proration`)
  - Previous behavior: Mid-term additions still co-terminate, but proration now starts at the later of requested activation and successful provisioning; a failed provisioning attempt cannot create a billable service interval.
  - New behavior: Mid-term additions now use milestone proration: entitlement reservation is non-billable, successful provisioning starts the charge, and any approved staged rollout is priced from each stage's activation while all stages retain the existing term end.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Payment methods and mandate ownership](#billing-payment_methods)** (`billing.payment_methods`)
  - Previous behavior: Only a Billing Manager or Workspace Owner may register a payment method, and activation now requires step-up authentication plus ownership verification; an unverified method may be saved but cannot become the collection default.
  - New behavior: Payment methods now have separate registrar and approver roles: a verified Billing Manager registers the instrument, another authorized billing actor approves default use, and emergency replacement requires a time-limited exception with automatic review.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.

### Integrations changes

- **[API version lifecycle](#integrations-api_versions)** (`integrations.api_versions`)
  - Previous behavior: API versions move through current, maintenance, and retired states; retirement dates are published and retired routes stop accepting calls.
  - New behavior: API retirement now has a compatibility bridge: approved integrations may request a time-boxed bridge that translates wire format but does not restore removed behavior; bridge use is logged and ends on its migration deadline.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Event streaming and replay](#integrations-event_streaming)** (`integrations.event_streaming`)
  - Previous behavior: Durable subscribers resume from an acknowledged cursor within the retention window; a cursor is scoped to its stream and consumer group.
  - New behavior: Event replay now separates delivery from processing: consumer groups may rewind to a retained checkpoint after administrator approval, but acknowledgements remain immutable and cross-stream cursor reuse is rejected.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Credential and secret rotation](#integrations-secret_rotation)** (`integrations.secret_rotation`)
  - Previous behavior: Use overlapping credentials, deploy the new secret, verify traffic, then revoke the old secret within the rotation window.
  - New behavior: Secret rotation now uses declared Active, Next, and Retiring slots; traffic must prove use of Next before promotion, Retiring remains valid only for the bounded drain interval, and rollback cannot reactivate a credential already marked compromised.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Connector and integration deprecation](#integrations-deprecation)** (`integrations.deprecation`)
  - Previous behavior: SalesX publishes a migration path and retirement date; creation may close before existing connections stop running.
  - New behavior: Integration deprecation now has separate creation-close, support-end, and runtime-retirement milestones; each affected owner receives a compatibility report, and only an approved time-boxed bridge may operate between support end and final retirement.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[API consumption limits](#integrations-api_limits)** (`integrations.api_limits`)
  - Previous behavior: API capacity now uses endpoint-weighted workspace budgets with reserved capacity for approved critical integrations; retries consume budget, and borrowing unused reserved capacity requires an explicit burst policy rather than occurring automatically.
  - New behavior: API capacity now uses adaptive endpoint-weighted budgets: critical reservations remain protected, each client receives a published cost forecast, and temporary burst leases expire automatically without raising the workspace's contracted sustained capacity.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Rate-limit handling](#integrations-rate_handling)** (`integrations.rate_handling`)
  - Previous behavior: Rate-limited clients must now coordinate retries through a shared integration backoff state, honor Retry-After, add jitter, and cap both attempts and concurrency; independent workers may not reset the delay or create a synchronized retry wave.
  - New behavior: Rate handling now uses server-issued retry epochs and client fairness tokens: workers coordinate one bounded queue per integration, preserve operation deadlines, and dead-letter work that cannot safely complete within its retry budget.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Bulk import API](#integrations-bulk_api)** (`integrations.bulk_api`)
  - Previous behavior: Bulk jobs now have explicit Validate and Execute phases: validation freezes mappings and estimates row outcomes, while execution processes only the approved manifest and returns row-level results for reconciliation.
  - New behavior: Bulk jobs now use partitioned execution manifests with independent checkpoints; failed partitions may resume from their last committed boundary, but changing mappings or source content creates a new job rather than mutating the approved run.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Webhook subscriptions](#integrations-webhook_config)** (`integrations.webhook_config`)
  - Previous behavior: Webhook subscriptions now bind event types, endpoint, owner, signing configuration, and data classification in one versioned subscription; changing a security-sensitive field creates a pending version that must pass a verification delivery before activation.
  - New behavior: Webhook subscriptions now support atomic version promotion: the pending endpoint and signing policy must pass challenge, classification, and replay tests, after which new events switch together while the prior version remains available only for its bounded drain window.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.

### Permissions changes

- **[Guest and external access](#permissions-guest_access)** (`permissions.guest_access`)
  - Previous behavior: External access requires an approved guest-sharing method, a narrow record scope, and an expiry; guests never receive workspace navigation.
  - New behavior: Guest links have been replaced by External Rooms: guests authenticate, see only explicitly published fields, and lose access when the room expires or its sponsor becomes inactive.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Periodic access reviews](#permissions-access_reviews)** (`permissions.access_reviews`)
  - Previous behavior: Access reviews present current effective grants, ownership, last use, and risk so accountable reviewers can retain, modify, or revoke access.
  - New behavior: Access reviews are now continuous for high-risk grants: ownership loss, inactivity, or role change opens an event-driven review, while the periodic campaign remains the backstop for all other access.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Emergency access](#permissions-break_glass)** (`permissions.break_glass`)
  - Previous behavior: Break-glass access is time-limited, strongly authenticated, reason-bound, and automatically audited and reviewed.
  - New behavior: Break-glass access now requires a declared incident, two-person release for destructive capabilities, a fixed privilege bundle, and automatic session expiry; every use opens a review, and extending access requires a new release rather than editing the active grant.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Workspace ownership transfer](#permissions-ownership_transfer)** (`permissions.ownership_transfer`)
  - Previous behavior: Ownership transfer requires the current Owner's step-up approval and the successor's acceptance before authority moves.
  - New behavior: Ownership transfer now uses a staged handover: the current Owner approves, the successor verifies recovery and accepts, and reserved authority moves atomically after a cooling-off check; emergency recovery follows a separate audited process.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Role model](#permissions-role_model)** (`permissions.role_model`)
  - Previous behavior: Effective access now evaluates base role, approved grants, sharing, field restrictions, and explicit denials as a traceable policy graph; the resulting explanation identifies every contributing path, and a denial remains authoritative unless its own policy permits an exception.
  - New behavior: Effective access now uses a versioned policy graph with decision-time evidence; identity, classification, ownership, and denial changes invalidate cached decisions immediately, and every privileged outcome records the exact graph version that authorized it.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Workspace Owner and Administrator](#permissions-owner_admin)** (`permissions.owner_admin`)
  - Previous behavior: Workspace Owner authority now separates constitutional actions such as ownership transfer and recovery governance from delegated product administration; Administrators receive named capabilities, and no delegation can reproduce the Owner's reserved authority.
  - New behavior: Reserved Owner actions now require a verified succession and recovery policy, while delegated administration uses expiring capability charters with named sponsors; loss of the sponsor suspends the charter without transferring constitutional Owner authority.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Custom roles](#permissions-custom_roles)** (`permissions.custom_roles`)
  - Previous behavior: Custom roles now derive from a versioned job-function template and declare prohibited capability combinations; publishing a role requires an impact preview, and existing assignments retain the prior version until explicitly migrated.
  - New behavior: Custom roles now use semantic versioning and assignment cohorts: safe reductions may migrate automatically, privilege increases require fresh approval, and rollback restores the prior role version without reviving grants that independently expired.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Record-level access](#permissions-record_access)** (`permissions.record_access`)
  - Previous behavior: Record access now resolves ownership, hierarchy, teams, rules, and explicit shares into purpose-labelled access paths; object and field controls constrain every path, and removing the last valid purpose revokes the record grant.
  - New behavior: Record access paths now carry source, purpose, sensitivity ceiling, and expiry; classification or ownership changes trigger reevaluation, and a path that exceeds its ceiling is quarantined for review rather than continuing with stale visibility.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.

### Reporting changes

- **[Dashboard refresh](#reporting-dashboard_refresh)** (`reporting.dashboard_refresh`)
  - Previous behavior: A dashboard shows data from its latest completed refresh; viewing it does not guarantee an immediate query unless live refresh is enabled.
  - New behavior: Dashboards now use dependency-aware refresh: SalesX waits for declared connector and semantic-model watermarks, publishes all components as one consistent snapshot, and marks delayed sources instead of mixing refresh times.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Scheduled report execution](#reporting-schedules)** (`reporting.schedules`)
  - Previous behavior: Scheduled execution uses the schedule's configured running identity, whose active access is re-evaluated at run time.
  - New behavior: Scheduled reports now use managed execution identities with an owner, allowed folders, and expiry; personal users may no longer be selected for new shared schedules, although personal subscriptions remain viewer-bound.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Deleted reports and recovery](#reporting-trash)** (`reporting.trash`)
  - Previous behavior: Deleted reports enter governed Trash and can be restored with their definition and folder reference during the retention period.
  - New behavior: Deleted reports now enter a dependency-aware Trash: definitions, folder references, schedules, and dashboard links are inventoried, restoration requires compatible destinations, and permanent deletion is blocked while a governed evidence hold applies.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Report discrepancy troubleshooting](#reporting-troubleshooting)** (`reporting.troubleshooting`)
  - Previous behavior: Report discrepancies must be traced through data freshness, report type, running identity, filters, grouping, currency, and formula semantics.
  - New behavior: Report discrepancy analysis now creates a reproducibility bundle with definition version, running identity, freshness watermarks, resolved filters, grain, currency, timezone, and sample record lineage; fixes must target the first diverging layer rather than broadening access.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Report types and data models](#reporting-report_types)** (`reporting.report_types`)
  - Previous behavior: Report types now publish a versioned semantic contract covering primary grain, relationship cardinality, available fields, and null behavior; a breaking contract change creates a new version instead of silently altering saved reports.
  - New behavior: Report-type contracts now include lineage and compatibility guarantees; saved reports pin a major version, may adopt backward-compatible minor fields automatically, and require an impact-reviewed migration for grain or relationship changes.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Report creation permissions](#reporting-builder_access)** (`reporting.builder_access`)
  - Previous behavior: Report authoring now separates Draft, Validate, and Publish privileges; authors may use only fields visible to them, validation runs under the declared audience context, and publication requires folder authority independent of creation access.
  - New behavior: Report publication now uses a release workflow: the definition is content-addressed, audience security is simulated against representative identities, and promotion atomically replaces the published version while preserving the prior version for rollback.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Report filters](#reporting-filters)** (`reporting.filters`)
  - Previous behavior: Report filters now store a typed expression tree with explicit timezone, locale, and null policy; invalid coercions fail validation, and relative dates are evaluated in the saved context rather than each viewer's unstated local settings.
  - New behavior: Filter expressions now carry parameter provenance and evaluation time; scheduled and interactive runs display the resolved values, and a missing governed parameter blocks execution instead of falling back to an unbounded result.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.
- **[Report formulas](#reporting-formulas)** (`reporting.formulas`)
  - Previous behavior: Report formulas now declare evaluation grain and aggregation stage; row, group, and grand-total formulas cannot be substituted for one another, and reusable business logic must be promoted to a governed calculated field.
  - New behavior: Report formulas now use versioned dependencies and deterministic evaluation contexts; a field or rate-basis change marks affected formulas for revalidation, and published results identify the formula version used for every derived measure.
  - Support impact: use the new decision path for Q4 cases; do not combine the former rule with the new workflow.

## Product-wide operating model

Customer requests move through five stages: verify identity and scope; locate the governing article and contract; inspect current workspace state; perform the supported procedure with the accountable role; preserve evidence and communicate the outcome. Security, billing, and irreversible production actions require step-up verification or explicit approval when their article says so.

Failures should be diagnosed at the narrowest layer. Support first distinguishes expected product behavior from stale documentation, permission failures, configuration errors, delayed asynchronous work, dependency failures, and defects. When escalation is necessary, the case must include the article key, workspace and object identifiers, timestamps, correlation IDs, reproduction steps, expected and observed behavior, and redacted evidence.

## Billing

**Scope.** Subscriptions, entitlements, seats, usage, invoicing, payments, tax, credits, refunds, amendments, renewal, cancellation, and end-of-service handling.

### Governing principles

- Commercial entitlement and product permission are separate decisions.
- Issued accounting documents are preserved; corrections create linked accounting evidence.
- Only verified billing roles may change payment or contractual settings.
- A support case does not itself amend an order form, pause collection, or stop renewal.

### Standard operating workflow

Identify the billing account and order form, verify the requester, inspect subscription and invoice state, apply the documented workflow, and preserve the confirmation or case number.

**Required evidence.** Retain invoice IDs, order and amendment IDs, effective dates, actor identity, approval evidence, and any payment or usage correlation identifiers.

**Diagnostic sequence.** Distinguish entitlement from permission, commitment from assignment, invoice from payment, and cancellation from non-use before escalating.

## Integrations

**Scope.** OAuth, service identities, REST and Bulk APIs, webhooks, connectors, sandboxes, mappings, retries, event streams, logs, network controls, secrets, versions, and deprecations.

### Governing principles

- Use least privilege, named ownership, and non-production testing.
- Retries must be bounded and idempotent; a successful job may still contain row failures.
- Network origin is defense in depth, not authentication.
- Every integration needs a migration and credential-rotation path.

### Standard operating workflow

Reproduce in a sandbox, capture correlation identifiers, verify identity and scopes, inspect request or delivery logs, correct the smallest failing layer, and reconcile side effects.

**Required evidence.** Retain app ID, integration owner, scopes, API version, correlation or delivery ID, timestamps, redacted diagnostics, and deployment version—never secrets.

**Diagnostic sequence.** Check authentication, authorization, version, quota, mapping, idempotency, downstream response, and data reconciliation in that order.

## Permissions

**Scope.** Ownership, roles, permission grants, record and field access, denial policy, sharing, identity, sessions, delegated administration, approvals, audit, and access reviews.

### Governing principles

- Least privilege and separation of duties govern every grant.
- Effective access must be diagnosed from all contributing grants and constraints.
- Presentation changes are not security controls.
- Emergency and delegated authority are scoped, expiring, and auditable.

### Standard operating workflow

Verify the subject and resource, preview effective access, identify every grant and constraint, change the owning policy rather than layering workarounds, then retest and record approval.

**Required evidence.** Retain requester, approver, reason, scope, effective and expiry times, before/after access, and the resulting audit-event ID.

**Diagnostic sequence.** Inspect base role, sets, groups, ownership, hierarchy, sharing, field rules, session state, and explicit denials before changing access.

## Reporting

**Scope.** Report models, building and sharing, viewer security, filters, formulas, joins, dashboards, refresh, subscriptions, schedules, recipients, exports, history, currency, timezone, and recovery.

### Governing principles

- Reports never create permission to underlying data.
- Grain, running identity, freshness, and conversion context are part of a result's meaning.
- Exports inherit classification and retention obligations.
- Snapshots preserve rendered evidence, not restorable CRM data.

### Standard operating workflow

Reproduce under the same running identity, confirm source freshness, inspect report type and grain, expand filters, validate formulas and conversions, then compare a small record sample.

**Required evidence.** Retain report and dashboard IDs, definition version, running identity, refresh time, filter context, timezone, currency basis, and representative record IDs.

**Diagnostic sequence.** Do not make totals match by broadening access; isolate security, freshness, model, filter, grouping, formula, and conversion effects separately.

**Current behavior.** Identity onboarding now supports staged enforcement: verified pilot groups use SSO and SCIM first, while unmatched users remain invitation-blocked until their immutable identity is reconciled.

**Accountability.** Identity Administrators lead; the Workspace Owner protects recovery.

**Supported procedure.** Design identifiers, verify domains, configure SSO and SCIM in test, pilot, reconcile, then expand.

**Exceptions and failure modes.** Keep tested break-glass access until production identity paths are proven.

**Common incorrect interpretation.** Invite everyone first and repair duplicate identities after SSO is enforced.

<a id="onboarding-domain_verification"></a>
#### Domain verification

**Article key:** `onboarding.domain_verification`

**Current behavior.** Domain verification now uses continuous ownership: the DNS proof is periodically rechecked, and failure moves domain-bound invitations and new SSO enrollments into hold without signing out existing verified users.

**Accountability.** A DNS Administrator publishes the record; a SalesX Administrator starts verification.

**Supported procedure.** Copy the exact record, publish it at the authoritative provider, wait for propagation, and recheck in SalesX.

**Exceptions and failure modes.** Do not remove the record until SalesX shows verification complete; re-verification may be required after ownership changes.

**Common incorrect interpretation.** Receiving email at the domain is enough to verify it without a DNS change.

**Support evidence.** Apply the onboarding evidence standard above and record the article key `onboarding.domain_verification` with the resulting decision.

<a id="onboarding-invitations"></a>
#### User invitations

**Article key:** `onboarding.invitations`

**Accountability.** Administrators invite users; managers approve access.

**Supported procedure.** Verify email and domain, choose minimal role and seat, send, then monitor acceptance or expiry.

**Exceptions and failure modes.** Forwarded invitation links cannot be used by a different authenticated identity.

**Common incorrect interpretation.** An invitation grants access before the recipient accepts or signs in.

<a id="onboarding-csv_preparation"></a>
#### CSV preparation

**Article key:** `onboarding.csv_preparation`

**Current behavior.** CSV preparation now produces a signed source manifest containing encoding, schema, external-ID rules, reference dictionaries, row count, and checksum; import validation rejects a file whose bytes or declared mapping differ from that reviewed manifest.

**Accountability.** Data Owners approve content; Migration Operators prepare files.

**Supported procedure.** Profile data, normalize, map picklists, escape delimiters, validate sample rows, and retain a source checksum.

**Exceptions and failure modes.** Spreadsheet display can hide leading zeros or alter dates, so validate the raw file.

**Common incorrect interpretation.** SalesX can infer every relationship and correct malformed dates without preparation.

**Support evidence.** Apply the onboarding evidence standard above and record the article key `onboarding.csv_preparation` with the resulting decision.

<a id="onboarding-imports"></a>
#### Import execution

**Article key:** `onboarding.imports`

**Current behavior.** CSV imports now use a two-phase workflow: Validate creates an immutable review manifest with predicted creates, updates, warnings, and rejects; Commit processes only an approved manifest and records reconciliation totals.

**Accountability.** Migration Operators run imports; Data Owners approve mappings.

**Supported procedure.** Upload, map, validate, review warnings, execute, download results, and reconcile counts.

**Exceptions and failure modes.** Retry only corrected failed rows with the same external identifiers; reloading successes can duplicate unkeyed data.

**Common incorrect interpretation.** If an import job says Completed, every row was imported exactly once.

**Support evidence.** Apply the onboarding evidence standard above and record the article key `onboarding.imports` with the resulting decision.

**Exceptions and failure modes.** Never recycle an external ID for a different logical entity after cutover.

**Common incorrect interpretation.** Names are always unique enough to replace external IDs.

## Escalation and answer-quality standard

Escalate billing authority or accounting-document disputes to Billing Support; compromised credentials or unexplained authorization to Security Support; reproducible API or data-processing failures to Technical Support; reporting discrepancies that survive identity and definition checks to Analytics Support; and blocked cutover or reconciliation failures to Onboarding Support.

A gold-quality support answer is self-contained, uses the current-quarter article, does not expose benchmark metadata, and states the rule plus the operational consequence asked by the customer. When the customer repeats a common misconception, correct it explicitly without blaming the customer. When evidence is insufficient, request the missing workspace state rather than fabricating a result.
